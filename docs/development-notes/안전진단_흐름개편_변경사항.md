# 안전진단 서비스 흐름 개편 변경사항

- 작성일: 2026년 8월 17일
- 작업 브랜치: `feat/ai-frontend`
- 변경 목적: STEP 1에서 사업장의 큰 작업·위험 범주를 확인해 제조업 기준 98개 중대 SIF를 25~35개로 선별하고, 체크리스트 응답 이후 최종 위험도를 진단한다.

## 1. 변경 배경

기존 흐름은 사업장 기본정보만 입력한 직후 사고확률과 위험 분석 결과가 표시되어 다음과 같은 문제가 있었다.

- 입력한 정보가 적은데도 구체적인 예측 결과가 나와 결과의 근거가 약해 보였다.
- 사용자의 실제 현장 안전관리 상태가 반영되기 전에 위험도가 표시됐다.
- 체크리스트가 진단 이후에 배치되어 위험도 계산과 분리된 기능처럼 보였다.

이를 해결하기 위해 사업장 상세정보와 체크리스트 미비 항목을 함께 반영한 뒤 최종 진단 결과를 제공하도록 흐름을 변경했다.

## 2. 최종 사용자 흐름

1. 사업장정보
2. 중대 체크리스트 및 최종 위험도 진단
3. 유사 재해사례
4. 예방가이드

핵심 원칙은 다음과 같다.

- STEP 1에서는 공통 사업장정보와 큰 작업·위험 범주를 선택한다.
- STEP 2에서는 현장 작업을 선택하고 관련 체크리스트에 모두 응답한다.
- 최종 위험도는 체크리스트 제출 이후에만 표시한다.
- STEP 3과 STEP 4는 앞에서 만들어진 진단 결과와 미비 항목을 기준으로 개인화한다.

## 3. 단계별 화면 변경사항

### STEP 1. 사업장정보

STEP 1의 목적을 위험도 예측이 아닌 SIF 선별로 변경했다. 특정 업종에만 해당하는 기계 수, 안전장치 상태, 적재 위치 등은 공통 필수 입력에서 제거했다.

- 사업장명
- 업종 및 세부 업종
- 지역 및 상세 주소
- 근로자 수
- 작업·위험 범주 복수 선택
  - 기계·설비 작업
  - 차량·운반 작업
  - 고소 작업
  - 전기 작업
  - 화기 작업
  - 화학물질 취급
  - 밀폐공간 작업
  - 건설·해체 작업
  - 적재·보관 작업
  - 일반 작업 중심

입력값과 작업·위험 범주가 누락되면 다음 단계로 이동하지 않는다. `일반 작업 중심`은 다른 위험 범주와 동시에 선택되지 않도록 처리했다. 이 단계에서는 위험 결과를 표시하지 않고 선별된 체크리스트로 이동한다.

주요 파일:

- `frontend/src/app/components/Step1Input.tsx`
- `frontend/src/app/types/safety.ts`

### STEP 2. 중대 체크리스트 및 최종 위험도 진단

기존 STEP 4에 있던 체크리스트를 STEP 2로 이동하고 최종 진단과 결합했다.

- 사용자가 실제 수행하는 작업유형을 먼저 선택한다.
- 선택한 작업과 관련된 중대 문항만 표시한다.
- 각 문항에 `예`, `아니오`, `해당 없음`으로 응답한다.
- 모든 문항에 응답하기 전에는 제출 버튼과 위험 결과가 활성화되지 않는다.
- `해당 없음` 응답은 미비 위험 계산에서 제외한다.
- 체크리스트 제출 후 최종 위험점수, 위험등급, 기본 위험, 미비 항목 위험, 주요 재해유형을 표시한다.
- 기존의 `사고확률` 표현은 `종합 위험유형 비중`으로 변경했다.

진단 결과는 다음 정보를 함께 반영한다.

- 동종 사업장 통계 및 ML 분석 결과
- STEP 1에서 선택한 작업·위험 범주
- STEP 2에서 `아니오`로 답한 체크리스트 항목과 위험 가중치

SIF 선별 규칙은 다음과 같다.

1. 모든 사업장에 적용할 수 있는 공통 중대문항을 우선 포함한다.
2. 같은 업종에서 선택 범주와 일치하는 문항을 포함한다.
3. 같은 업종의 문항이 부족하면 다른 업종의 동일 작업 범주 문항으로 보완한다.
4. 그래도 25개보다 적으면 해당 업종의 고위험 문항을 위험가중치 순으로 보완한다.
5. 후보가 많으면 최대 35개까지만 제공한다.

### STEP 3. 유사 재해사례

- 최우선 재해유형을 포함한다.
- 체크리스트 미비 항목을 포함한다.
- 추천 근거를 화면에 표시한다.
- 사례별 유사도와 재발 방지 대책을 제공한다.

### STEP 4. 예방가이드

- 체크리스트에서 확인된 미비 항목을 재해유형별로 묶는다.
- 위험 비중에 따라 개선 우선순위를 정한다.

- 연결된 법령 근거를 제공한다.
- 종합 PDF 리포트를 다운로드할 수 있도록 기존 보고서 기능과 연결한다.

## 4. 파트별 변경사항

### 4.1 Frontend

- 라우팅을 `/` → `/checklist` → `/cases` → `/prevention` 순서로 변경했다.
- 기존 `/report` 접근은 `/checklist`로 이동시킨다.
- STEP 1을 특정 설비 상세입력 대신 10개 작업·위험 범주를 복수 선택하는 UI로 변경했다.
- 선택 범주를 진단 세션에 저장하고 STEP 2 체크리스트 조회 파라미터로 전달한다.
- STEP 2에서 체크리스트 제출 후에만 진단 결과를 표시한다.
- STEP 2의 세부 작업유형 재선택 UI를 제거하고 STEP 1 선별 결과를 바로 표시한다.
- STEP 3에 진단 기반 추천 근거를 추가했다.
- STEP 4를 맞춤 예방가이드와 PDF 다운로드 화면으로 변경했다.
- 실제 서버가 없는 개발 환경에서도 전체 흐름을 확인할 수 있도록 예시 데이터를 보완했다.

### 4.2 Backend

- 사업장 생성 요청, 응답, 엔티티에 상세정보 필드를 추가했다.
- 체크리스트 조회 API에 반복 가능한 `scope` 파라미터를 추가했다.
- 작업유형·재해유형·질문 문구를 이용해 큰 범주와 SIF를 연결한다.
- 공통 → 같은 업종 관련 → 타 업종 동일 범주 → 업종 고위험 순으로 25~35개를 선별한다.
- 체크리스트의 `아니오` 응답을 재해유형별 위험 신호로 집계한다.
- 집계된 위험 신호와 사업장 상세정보를 ML 서버 요청에 포함한다.
- 진단 결과와 미비 문항을 유사사례 검색 문맥으로 전달한다.
- 최신 체크리스트 제출 결과를 이용하는 맞춤 예방가이드 API를 추가했다.
- PDF 보고서에 추가 사업장 정보와 맞춤 예방가이드를 포함했다.

추가 API:

```http
GET /api/workplaces/{workplaceId}/prevention-guide
```

### 4.3 ML

STEP 1의 작업·위험 범주는 체크리스트 선별에 사용하며, 그 자체를 사고확률로 해석하지 않는다. 최종 ML 위험유형 비중은 체크리스트 제출 이후에만 계산한다.

- 위험 예측 요청에 다음 필드를 받을 수 있도록 스키마를 확장했다.
  - 기계·설비 종류 및 수량
  - 안전장치 설치 상태
  - 적재 위치 및 방식
  - 체크리스트 위험 신호(`risk_signals`)
- ML 결과, 체크리스트 미비 항목, 사업장 프로필 신호를 혼합해 재해유형별 위험 비중을 계산한다.
- 체크리스트가 있는 경우 ML 55%, 체크리스트 35%, 사업장 프로필 10% 비율로 결합한다.
- 유사사례 검색 API에 진단 문맥(`query_context`)을 추가했다.
- 산출값은 보정된 실제 사고확률이 아니라 진단 우선순위를 위한 위험유형 비중으로 사용한다.

### 4.4 Database

`workplace` 테이블에 다음 컬럼을 추가하는 마이그레이션을 작성했다.

아래 필드는 이전 상세정보 설계를 위해 추가됐으나 현재 STEP 1에서는 필수로 입력하지 않는다. 컬럼과 API 필드는 nullable 상태로 유지해 향후 업종별 추가질문에 사용할 수 있도록 했다.

- `machine_type`
- `machine_count`
- `safety_device_status`
- `storage_location`
- `storage_method`

- SIF 선별 단위 테스트 3건 성공

  - 해당 업종 문항이 없으면 타 업종의 동일 작업 범주 문항 활용

- ML 위험 예측 요청 스키마 생성 확인
- 인앱 브라우저에서 STEP 1부터 STEP 4까지 전체 흐름 확인
- 인앱 브라우저에서 큰 범주 3개 선택 후 예시 SIF 30개 선별 확인
- `일반 작업 중심`과 다른 위험 범주가 동시에 선택되지 않는 것 확인
- 체크리스트 제출 전 위험 결과가 표시되지 않는 것 확인

### 제한사항

- Docker 엔진이 실행되지 않아 Testcontainers 기반 DB 통합 테스트는 수행하지 못했다.
- 현재 로컬 인앱 브라우저는 실제 BE·DB 대신 개발용 예시 데이터를 사용한다.
- 작업공간 Python 환경에 `shap` 패키지가 없어 ML 서버 전체 런타임 기동은 확인하지 못했다.

## 7. 배포 및 통합 전 확인사항

- `SCHEMA_26_diagnosis_flow.sql`을 대상 DB에 적용한다.
- Backend, ML 서버, Frontend를 함께 실행해 실제 API 통합 흐름을 확인한다.
- 운영 DB의 98개 제조업 중대 SIF에서 범주 조합별 선별 품질을 현장 담당자와 검토한다.
- 실제 사업장 생성 응답에 새 상세정보 필드가 포함되는지 확인한다.
- 체크리스트 `아니오` 응답이 위험도와 예방가이드에 반영되는지 확인한다.
- 실제 사례 데이터에서 진단 문맥 기반 검색 품질을 확인한다.
- PDF에 사업장 상세정보와 맞춤 예방항목이 정상 출력되는지 확인한다.
- Docker 실행 환경에서 통합 테스트를 다시 수행한다.

## 8. 최종 정리

이번 개편의 핵심은 위험 결과를 먼저 보여주는 구조에서 벗어나 다음 근거를 모두 확보한 뒤 최종 진단을 제공하는 것이다.

1. 공통 사업장정보와 큰 작업·위험 범주
2. 98개 중 25~35개로 선별된 중대 SIF 체크리스트
3. 체크리스트에서 확인된 실제 미비 항목

따라서 변경된 서비스는 `사업장정보 → 체크리스트·최종진단 → 유사 재해사례 → 예방가이드`라는 일관된 흐름으로 동작한다.
