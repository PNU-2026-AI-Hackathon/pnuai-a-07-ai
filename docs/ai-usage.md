# AI 도구 활용 및 고도화

SafeWork AI는 생성형 AI를 단순 코드 생성 도구로 사용하지 않고, **설계자가 구현 방향과 책임 범위를 먼저 정의한 뒤 반복 작업·코드 분석·데이터 정제·문서화를 보조하는 도구**로 활용했습니다. 또한 제품 내부의 AI 기능과 개발 과정에서 사용한 AI 도구를 구분하여 적용했습니다.

## 1. 활용한 AI 도구 및 범위

| 구분 | AI 도구 | 활용 범위 |
|---|---|---|
| Backend | Claude Code (Claude Opus) | Spring Boot API 구현, PostgreSQL 함수 연동, 통합 테스트 작성, 디버깅, API 명세·리팩터링 |
| Database | Claude, ChatGPT, Prism | DB 스키마·PL/pgSQL 함수 및 데이터 수집 스크립트 작성, 데이터 분류·정제, 협업 문서 정리 |
| ML / Data | Claude Haiku, Claude Code | 산업재해 발생형태 분류, SIF 체크리스트 생성, 법령 매핑, RAG/API 코드 작성 및 성능 분석 |
| Frontend | Figma Make, OpenAI Codex | UI 초안, React·TypeScript 구현, Router/Context 구성, API 연동, 오류 분석 및 리팩터링 |
| 서비스 AI | Gemini API (`gemini-flash-lite-latest`) | 검색된 법령을 근거로 법령 상담·사고 대처 설명 생성 |
| 임베딩 | sentence-transformers | 법령 조문 및 재해사례 벡터화, 체크리스트-법령 및 유사사례 검색 |

데이터 구축 단계에서는 미분류 산업재해 사례의 발생형태를 분류하고, 실제 SIF 사례를 근거로 체크리스트 후보를 생성하는 데 LLM을 활용했습니다. 법령 매핑은 생성형 AI가 처음부터 조문을 선택하지 않고, **임베딩 유사도로 상위 후보를 좁힌 뒤 LLM이 최종 후보를 선택하는 2단계 구조**로 구성했습니다.

제품의 법령 상담에서도 동일한 원칙을 적용했습니다. 키워드 검색과 임베딩 검색으로 실제 DB의 관련 조문을 먼저 결정한 뒤 Gemini는 **검색된 조문 안에서만 답변 문장을 생성**합니다. 생성형 AI 호출이 실패하거나 API Key가 없는 경우에는 검색된 법령을 그대로 제공하도록 하여 AI를 서비스의 단일 장애점으로 두지 않았습니다.

## 2. AI 생성 결과의 검증 및 수정

AI가 생성하거나 제안한 코드와 데이터를 그대로 반영하지 않고 **실행 결과와 원본 데이터를 기준으로 재검증**했습니다.

백엔드는 Testcontainers로 실제 PostgreSQL을 실행하고 저장소의 스키마를 적재하여 **79건의 통합 테스트**를 수행했습니다. PostgreSQL 전용 enum, 배열, `jsonb`, PL/pgSQL 함수까지 실제 운영 환경과 동일하게 검증했으며, 테스트 통과 이후에도 실제 서버에서 주요 사용자 흐름을 다시 확인했습니다.

DB 함수와 SQL은 DBeaver에서 직접 실행하여 입력값에 따른 반환 결과를 검증했고, 데이터 적재 후에는 건수와 매핑 결과를 검증 쿼리로 확인했습니다. LLM이 생성한 체크리스트는 반드시 **근거 재해사례 인덱스를 포함하도록 프롬프트를 제한**하고, 근거가 없는 문항은 자동 제외했습니다. 체크리스트-법령 연결은 임베딩 후보군과 LLM 판단을 결합한 뒤 DB View를 통해 전수 확인할 수 있도록 구성했습니다.

ML 서버에서는 AI가 제안한 원인이나 성능 수치를 그대로 사용하지 않고 실제 코드를 실행해 재측정했습니다. SHAP Explainer가 요청마다 생성되던 병목 역시 실행 시간을 반복 측정한 뒤 캐싱하도록 수정했습니다. 코드의 작성 범위와 변경 이력은 `git log`, `git blame`, `git diff`로 확인했습니다.

프론트엔드는 TypeScript/Vite 프로덕션 빌드로 문법 및 모듈 오류를 확인하고, **사업장 등록 → 체크리스트 → 위험도 진단 → 유사 재해사례 → 예방가이드** 흐름을 브라우저에서 직접 실행했습니다. 백엔드 DTO와 요청·응답 필드 및 자료형도 비교하여 불일치 사항을 수정했습니다.

AI의 판단이 잘못된 경우에는 코드를 폐기하거나 다시 설계했습니다. 예를 들어 사고 후 법적 의무를 Java 코드에 하드코딩한 구현은 DB에 이미 기한·기관·근거 법령이 구조화되어 있음을 확인한 뒤 삭제하고 DB 조회 방식으로 변경했습니다. 또한 AI가 실제 존재하는 데이터를 없다고 판단하거나 오래전에 반영된 스키마를 누락된 것으로 판단한 사례가 있어, **AI의 설명보다 저장소·DB·실행 결과를 우선적인 근거로 사용**했습니다.

마지막으로 API Key와 같은 민감정보는 환경변수로 분리하고 사전 커밋 훅을 적용하여 저장소에 포함되지 않도록 관리했습니다.

> **활용 원칙:** AI는 구현과 분석의 속도를 높이는 보조 도구로 사용하되, 최종 설계 판단과 코드·데이터의 정확성 검증은 개발자가 직접 수행했습니다.
