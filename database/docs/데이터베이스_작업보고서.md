# SafeWork AI — 데이터베이스 파트 작업 보고서

| 항목 | 내용 |
|---|---|
| 프로젝트 | SafeWork AI (산재지킴이 AI) · 제7회 PNU 창의융합AI해커톤 융합트랙 |
| 담당 | 강주호 — 데이터베이스 구축 및 데이터 전처리 |
| DBMS | PostgreSQL 18 (`ai_safework`) · 클라이언트 DBeaver |
| 문서 성격 | 데이터베이스 파트 자체 작업 보고 (중간보고회 설명용) |

> 이 문서는 SafeWork AI의 데이터 기반을 혼자 설계·구축·검증한 과정을 정리한 것이다. 스키마 설계에 그치지 않고 실제 공공데이터 64만 건을 적재하고, 위험도 진단 로직까지 SQL로 구현·검증한 전 과정을 담는다.

---

## 1. 한눈에 보는 성과

데이터베이스 파트는 "테이블만 만드는" 역할을 넘어, **데이터 수집 → 정제 → 무결성 → 분석 로직**까지 데이터 계층 전체를 책임졌다.

| 영역 | 산출물 | 규모/상태 |
|---|---|---|
| 스키마 설계 | 서비스 계층 테이블 + 뷰 | 32개 테이블 + 3개 뷰 |
| 학습 데이터 | 산재 마이크로데이터 등 5개 테이블 | **647,044행 적재** |
| 법령 데이터 | 법령 원문 수집·청킹 | law_article 2,547 + law_chunk |
| 데이터 무결성 | 코드 마스터 + 외래키 | 마스터 54값 + FK 12개 |
| 분석 데이터 | 업종 벤치마크 집계 | **4,748행** |
| 진단 로직 | 콜드스타트 스코어링 함수 | 함수 2개, 실측 검증 완료 |
| 진단 근거 | SIF 기반 체크리스트 | 20문항 (법령·SIF 연결) |

핵심은 **전부 실데이터로 동작하는 것을 실측으로 증명**했다는 점이다. mock(가짜 구현)이 아니라, 실제 사업장 조건을 넣으면 위험점수가 근거와 함께 산출된다.

## 2. 데이터베이스 아키텍처

### 2.1 2계층 설계

"모델이 학습하는 데이터"와 "사용자가 만들어내는 데이터"는 수명주기와 접근 패턴이 완전히 다르다. 전자는 공공데이터를 배치로 적재하고 바뀌지 않으며, 후자는 실시간으로 쓰이고 갱신된다. 이 둘을 물리적으로 분리해 참조 데이터가 서비스 트랜잭션에 오염되지 않게 했다.

| 계층 | 성격 | 대상 테이블 |
|---|---|---|
| 참조 데이터 계층 | 읽기 전용, ML 학습·조회 | accident_case, sif_case, coldstart_baseline, size_injury_rate, office_stat |
| 서비스 데이터 계층 | 읽기/쓰기, 애플리케이션 | 회원·사업장·진단·법령·채용·리포트 등 |

### 2.2 DBMS 선택 — MySQL에서 PostgreSQL로

기획서 기술스택은 MySQL 8.0이었으나, 데이터 파트를 직접 운영하는 입장에서 아래 근거로 PostgreSQL로 변경을 결정하고 팀에 공유했다.

- `pg_trgm` 유사도 인덱스 — 법령·재해사례 부분일치 검색
- 표현식 인덱스, JSONB(진단 피처 스냅샷 저장), 배열 타입(답변 근거 배열)
- `mode() WITHIN GROUP`, `PERCENT_RANK` 등 집계·통계 함수가 진단 로직 구현에 유리

JPA 사용 시 백엔드 코드 변경은 최소이며 드라이버·방언 설정만 조정하면 된다는 점을 확인하고, 통합 연동 전에 합의하도록 리스크로 관리했다.

## 3. 학습 데이터 구축

### 3.1 소스 선정

모든 학습 데이터는 한국산업안전보건공단(KOSHA)·고용노동부가 공공데이터포털에 공개한 정부 원천 데이터에서 수집했다. 출처가 공신력 있는 공공데이터라는 점 자체가 진단 결과의 신뢰 근거가 된다.

| 소스 | 데이터ID | 적재 테이블 | 전처리 요지 |
|---|---|---|---|
| 산업재해통계 마이크로데이터 | 15127634 | accident_case | 업종 구분 후 건 단위 정제, 14개 피처 표준화 |
| 산업재해 고위험요인(SIF) 목록 | 15140383 | sif_case | 위험요인·상황·대책 텍스트 정제 |
| 산업중분류별 재해율 | 15064270 | size_injury_rate·베이스라인 | 계산된 재해율을 직접 사용 |
| 규모별 근로자수 | 15064274 | (비중 계산 전용) | 규모 구간별 전국 비중 산출에만 활용 |
| 연령별 사고사망자수 | 15084668 | (검증·보정 전용) | 연령 분포 EDA·편향 점검 |

**베이스라인 설계 결정:** 업종별 근로자수 데이터는 공개돼 있지 않다. 그래서 "재해건수 ÷ 근로자수"를 직접 계산하는 대신, 이미 재해율이 산출되어 있는 산업중분류별 재해율 데이터를 그대로 베이스라인으로 사용했다. 불필요한 재계산을 피하고 정부가 검증한 수치를 신뢰하는, 데이터 정합성 측면에서 안전한 선택이다.

### 3.2 적재 결과

| 테이블 | 적재 행수 | 내용 |
|---|---|---|
| accident_case | **640,134** | 산재 마이크로데이터 (2017~2025, 14개 피처) |
| sif_case | 6,032 | SIF 고위험요인 사례 |
| coldstart_baseline | 609 | 업종×규모×지역 베이스라인 |
| size_injury_rate | 220 | 규모별·연도별 재해율 (2004~) |
| office_stat | 49 | 관서별 재해·사망자 수 |
| **합계** | **647,044** | |

`accident_case`는 요약표가 아니라 **건 단위 마이크로데이터 64만 건**으로, 연도·업종·재해유형·규모·성별·연령·근속·재해정도·지역·관서·질병/사망 등 14개 피처를 갖는다. XGBoost가 업종·규모·지역 조합별로 통계적으로 유의미한 패턴을 학습할 수 있는 규모다.

### 3.3 부산·경남 특화의 실증 근거

적재 데이터가 프로젝트의 지역 특화 주장을 수치로 뒷받침한다.

- 전체 64만 건 중 **경남 58,826 + 부산 35,297 = 94,123건** — 지역 특화 모델 학습에 충분한 표본
- 사망사고(`death_flag=1`) **10,902건** 확보 — 중대재해 예측(Recall 중시) 학습 라벨
- 2017~2025년 9개 연도 고른 분포 — 시간 편향 보정을 위한 연도 가중치 적용 가능

### 3.4 데이터 품질·편향 대응

산재 마이크로데이터에 내재한 편향을 스키마·데이터 차원에서 다뤘다. `year` 컬럼(2017~2025)으로 최근 연도 가중치 적용이 가능하게 했고, 조인 키에 대리키와 제약을 부여했으며, 코드 마스터로 도메인을 통일했다(5장 참조). 신고 편향·업종 불균형은 통계 파트(신찬우)와 연계해 보정 전략을 세운다.

## 4. 법령 데이터 구축

### 4.1 목표와 원칙

법령 RAG 챗봇이 "우리 사업장은 무엇을 위반했나"에 **근거 조항과 함께** 답하려면, 정확하고 출처가 명확한 법령 원문이 필요하다. 핵심 원칙은 "많이 모으기"가 아니라 **"출처를 잃지 않기"** 다. 틀린 법령 안내는 단순 오답이 아니라 사용자를 법적 위험에 빠뜨리는 오답이기 때문이다.

### 4.2 수집 파이프라인

국가법령정보 공동활용 API(법제처)를 2단계(목록 조회 → 본문 조회)로 호출해 조·항 단위로 파싱, `law_article`에 적재하는 Python 파이프라인을 구현했다.

| 법령 | 조문행 |
|---|---:|
| 산업안전보건법 | 565 |
| 산업안전보건법 시행령 | 231 |
| 산업안전보건법 시행규칙 | 619 |
| 산업안전보건기준에 관한 규칙 | 1,102 |
| 중대재해 처벌 등에 관한 법률 | 30 |
| **합계** | **2,547** |

### 4.3 직접 발견·수정한 데이터 품질 이슈 2건

파이프라인을 돌리며 육안 검수로 두 가지 문제를 발견하고 원인을 파악해 수정했다. 이는 AI가 생성한 코드를 그대로 쓰지 않고 실제 응답을 검증했음을 보여준다.

- **편·장 제목 혼입:** "제1장 총칙" 같은 구조 헤더가 가짜 조문으로 섞여 조문번호가 중복됐다. `조문여부='전문'` 필터로 제거(592 → 565행).
- **인라인 태그 잘림:** 조문 안에 인용 링크 태그가 있으면 그 뒤 텍스트가 잘렸다. XML 텍스트 전체 수집(`itertext`) 방식으로 수정하고, DBeaver에서 제4조 제1항 1~9호 전체 복원을 확인했다.

### 4.4 청킹 — RAG 품질의 핵심

`law_article`을 검색 단위 `law_chunk`로 변환했다. 각 청크에 출처 헤더 `[법령명 제N조(제목) 제M항]`를 붙이고, 긴 조문은 호 단위로 분할하며 헤더를 반복 삽입했다.

**청크 경계를 조·항 경계와 일치**시킨 것이 핵심 결정이다. 고정 길이로 자르면 "제38조 제1항"의 중간이 잘려 검색은 되지만 인용이 부정확해지는데, 이는 법령 챗봇에서 가장 나쁜 상태다. 반대로 "짧은 항 병합"은 채택하지 않았다 — 한 청크가 두 조항을 가리키면 인용이 모호해지기 때문이다. 인용 정확도를 최우선으로 뒀다.

## 5. 데이터 무결성 — 코드 마스터 + 외래키

이 프로젝트 최대의 숨은 리스크는 **문자열 도메인 불일치**였다. 사용자가 등록한 사업장의 업종(`workplace.industry`)과 통계 데이터의 업종(`accident_case.industry`)이 한 글자라도 다르면, 콜드스타트 조회가 통째로 빈 결과를 낸다.

이를 막기 위해 적재된 실데이터 64만 건에서 실제 값을 추출해 코드 마스터를 채웠다.

| 마스터 | 값 수 | 예시 |
|---|---|---|
| code_industry | 4 | 건설업 / 제조업 / 운수창고통신업 / 전기가스증기수도사업 |
| code_size_class | 10 | 5인 미만 ~ 1,000인 이상 |
| code_region | 16 | 전국 광역 (부산·경남 = 타깃) |
| code_accident_type | 24 | 끼임 / 떨어짐 / 부딪힘 … |

그 위에 참조·서비스 테이블에 **외래키 12개**를 걸었다. 특히 `workplace`의 업종·규모·지역 FK가 핵심으로, 사용자 입력을 마스터 값으로만 받게 강제하여 콜드스타트 조인이 구조적으로 실패할 수 없게 만들었다. accident_case 64만 건에 FK를 걸 때 검증을 통과했다는 것은 **전 데이터의 도메인 값이 마스터와 완전히 일치**함을 증명한다.

## 6. 분석 기능 데이터 — 업종 벤치마크

"동종업종 평균 대비 내 사업장" 비교 기능을 위해, accident_case 64만을 업종×규모×지역×연도로 집계해 `industry_benchmark` **4,748행**을 산출했다. 그룹별 사고 건수·사망비율·질병비율·최빈 재해유형과 규모별 재해율을 담는다.

실측 결과 하나가 프로젝트 서사를 강화한다. **소규모 사업장(5인 미만 부산 사망비율 2.29%)이 대기업보다 사망비율이 높은** 경향이 데이터로 확인됐다 — 전체 사망비율 1.70% 대비 소규모가 더 위험하다는 것으로, 소규모 특화 서비스의 필요성을 뒷받침한다.

## 7. 진단 로직 — 콜드스타트 스코어링

진단 이력이 없는 신규 사업장의 위험도(0~100)를 산출하는 PostgreSQL 함수 `fn_coldstart_score`를 구현했다. 실제 XGBoost 모델이 완성되기 전까지 그 자리를 실제로 채우는, 동작하는 로직이다.

**하이브리드 구조:**
- 베이스 0~60점 — `coldstart_baseline`의 중대재해비율을 전체 609개 그룹 중 백분위로 환산
- 체크리스트 0~40점 — 현장 체크리스트의 'NO'(미비) 응답 위험가중치 합 (중대문항 ×2)

**단계적 fallback:** 정확 매칭(업종×규모×지역)이 없으면 → 업종×규모 평균 → 업종 평균 순으로 내려간다. 데이터가 없는 조합에도 점수를 낼 수 있게 한, 콜드스타트의 본질적 문제에 대한 대응이다.

**설명가능성:** 베이스/체크리스트 분해값과 매칭 수준·최빈 재해유형을 함께 반환하고, 진단 결과를 `raw_features`(JSONB)에 저장해 "왜 이 점수인지"를 사후 설명(SHAP 유사)할 수 있게 했다.

**실측 검증:** 제조업×5인미만×부산 가상 사업장으로 검증했다. 체크리스트 없을 때 32.81점(MEDIUM), 3개 위험문항에 'NO' 응답 시 **45.31점(MEDIUM)**으로 상승 — 베이스라인과 현장 체크리스트가 결합된 하이브리드 점수가 실제로 작동함을 확인했다.

## 8. 진단 근거 — SIF 기반 체크리스트

콜드스타트 점수의 현장 요소를 위해, 적재된 sif_case 6,032건에서 업종별 빈발 고위험 패턴을 추출해 **20문항**을 설계했다.

- 건설 10문항 — 추락 중심(비계·지붕채광판·사다리·개구부·달비계 등) + 굴착 붕괴
- 제조 10문항 — 비정형작업 LOTO·컨베이어·지게차·크레인·산업용로봇·용접 등

각 문항은 **대표 SIF 사례와 실제 법령 조문에 연결**했다. law_ref의 조문 번호 14개를 적재된 `law_article`과 교차검증하여 전부 실재함을 확인했다(예: 제42조 추락의 방지, 제92조 정비 시 운전정지, 제191조 비상정지장치). 즉 "이 체크리스트 문항의 근거가 무엇이냐"는 질문에 **실제 재해사례와 법령 조항으로 답할 수 있다.**

## 9. 기술적 판단 기록

단순 지시 수행이 아니라, 각 단계에서 근거를 갖고 판단한 결정들이다.

| 결정 | 근거 |
|---|---|
| PostgreSQL 채택 | 유사도 검색·JSONB·통계함수가 진단/RAG에 유리 |
| 임베딩은 FAISS, DB엔 미저장 | 벡터 이중 저장 시 동기화 문제 → 원문·인덱스 참조만 DB 보관 |
| 파인튜닝 미사용, RAG 전용 | 모델이 법조문을 "기억"하면 없는 조항을 지어냄 → 검색-주입으로 방어 |
| 청크를 조·항 경계로 고정 | 인용 정확도가 법령 챗봇의 생명 |
| 코드 마스터를 실데이터에서 추출 | 초기 임의 시드값(영문)이 실데이터(한글)와 불일치함을 발견하고 교체 |
| 콜드스타트 fallback 3단계 | 데이터 없는 조합에도 진단 가능해야 함 |
| 답변 근거 강제 기록 | `cited_articles` 등으로 무근거 답변을 버그로 관리 |

트러블슈팅도 직접 처리했다: 국가법령정보 API 미승인 오류, XML 인코딩(psql 적재), 파이썬 인터프리터 이중 설치 문제, 대용량 덤프의 psql 복원 등 실환경 이슈를 해결하며 파이프라인을 완성했다.
