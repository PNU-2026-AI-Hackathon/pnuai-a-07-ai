### 핵심 설계 원칙

1. **판단만 제시하지 않고 근거를 함께 제공한다.**“위험합니다”에서 끝나는 것이 아니라 관련 법령 조문, 행정 기한, 담당 기관, 처벌 관련 정보를 함께 제공하여 사용자가 결과를 직접 검증할 수 있도록 한다.
2. **불확실할 때는 안전한 방향으로 안내한다.** 피해 정도 등 필수 정보가 불명확할 경우 관련 안전·법적 안내를 임의로 제거하지 않고, 확인이 필요한 조건과 근거를 함께 제공한다.
3. **일부 AI 기능이 실패해도 서비스 전체는 동작한다.** ML 서버 장애 시 통계·DB 기반 진단을 활용하고, 생성형 AI 호출이 실패하면 검색된 법령 조문 자체를 반환하는 방식으로 기능을 단계적으로 축소한다.
4. **판정 기준은 가능한 한 데이터 계층에서 일원화한다.** 위험도 계산과 법령 기반 판정 로직을 여러 애플리케이션에 중복 구현하지 않고 PostgreSQL 함수와 기준 데이터에 집중하여 로직 불일치를 줄인다.

# 1. 프로젝트 소개

## 1.1. 개발배경 및 필요성

2024년 1월 27일부터 중대재해처벌법의 적용 범위가 **상시근로자 5인 이상 사업장**으로 확대되면서 중소·영세 사업장 역시 안전보건관리체계를 구축하고 이행해야 할 필요성이 커졌다.

그러나 소규모 사업장은 대기업에 비해 안전 업무를 전담할 전문 인력과 비용을 확보하기 어렵다. 특히 사고가 발생했을 때 사업주가 즉시 확인해야 하는 정보는 단순히 “위험한 사고인가”가 아니다.

- 어떤 조치를 먼저 해야 하는가?
- 어떤 기관에 신고해야 하는가?
- 언제까지 신고해야 하는가?
- 어떤 법령에 근거한 의무인가?
- 현재 사업장의 어떤 항목을 우선 개선해야 하는가?

법령과 안전 관련 공공데이터는 공개되어 있지만 서로 다른 기관과 문서에 분산되어 있으며, 비전문가가 사고 직후 필요한 내용을 직접 검색하고 해석하기에는 어려움이 있다.

**SafeWork AI는 이러한 정보 비대칭을 줄이기 위해 개발한 50인 미만 사업장 중심의 AI 안전관리 조력자이다.**

단순히 사고 발생 가능성을 예측하는 데 그치지 않고,

**사고 전 예방 → 위험 진단 → 유사사례 확인 → 개선 → 법령 상담 → 사고 발생 후 대응**

과정을 하나의 서비스 흐름으로 연결하는 것을 목표로 한다.

> SafeWork AI는 전문 안전관리자 또는 법률 전문가를 대체하거나 최종적인 법적 판단을 내리는 서비스가 아니다.
> 
> 
> 실제 공공데이터와 법령 근거를 사용자가 이해하기 쉬운 형태로 연결하여 **판단과 대응을 보조하는 서비스**를 지향한다.
> 

## 1.2. 개발 목표 및 주요 내용

SafeWork AI의 개발 목표는 크게 세 가지이다.

### ① 사고가 발생하기 전에 위험요인을 찾는다

사업장의 업종·규모·지역·작업 범위와 실제 산업재해 데이터를 이용해 사업장과 관련성이 높은 위험요인을 제공한다.

835개 후보 문항을 정제해 서비스용 SIF 98개를 구성하고, 이 중 사업장별 25~35개의 관련 문항을 선별한다.

점검 결과는 통계 기반 위험도와 ML 위험 신호를 결합하여 예방 활동의 우선순위를 정하는 데 활용한다.

### ② 결과에 법적·데이터적 근거를 붙인다

법령 상담에서는 일반 생성형 AI가 자체 지식만으로 답을 생성하도록 하지 않는다.

먼저 실제 DB와 검색 시스템에서 관련 법령 조문을 검색하고, 생성형 AI는 검색된 근거 범위 안에서 답변을 구성한다.

답변에는 조문 번호와 관련 법령을 함께 제공하여 사용자가 원문을 확인할 수 있도록 한다.

### ③ 사고 발생 이후의 행동까지 지원한다

사고가 발생한 경우 사용자가 가장 먼저 필요한 정보를 다음 세 단계로 구분하여 제공한다.

- **즉시 조치**
- **법적 의무**
- **행정 처리**

신고 기관, 신고 기한, 관련 법령, 필요한 후속 절차를 하나의 흐름에서 확인할 수 있도록 설계했다.

### 데이터베이스

SafeWork AI의 데이터 계층은 PostgreSQL 18을 기반으로 구성했다.

주요 데이터는 다음과 같다.

- 산업재해 데이터 약 64만 건
- 법령 조문 3,608건
- 안전 점검 문항 835개
- SIF 실제 재해사례
- 판례 및 행정규칙
- 사업주 지원 정책
- 업종·규모·지역 코드
- 사고 후 행정절차 및 법적 근거

국가법령정보 공동활용 API와 공공데이터 API를 활용한 수집 스크립트를 저장소에 포함해 데이터 수집 과정을 재현할 수 있도록 했다.

주요 DB 함수는 다음과 같다.

- `fn_accident_law_basis` : 사고 유형에 따른 관련 법령 근거 조회
- `fn_prevention_guide` : 점검 미비 항목에 따른 개선 우선순위 산출
- `fn_coldstart_assess` : 통계 기반 초기 위험도 산출
- `fn_check_severe` : 산업안전보건법상 중대재해 기준 대조
- 기타 위험도·예방·사고 대응 관련 함수

PostgreSQL의 `enum`, `text[]`, `pg_trgm` 등의 기능을 적극 활용했다.

### ML 기반 위험 신호

산업재해 데이터를 6개 업종군으로 구분하여 **5개 태스크 × 6개 업종군 = 총 30개 LightGBM 모델**을 학습했다.

현재 웹 서비스에서는 이 가운데 **제조업, 건설업, 운수·창고·통신업, 전기·가스 관련 업종의 4개 업종군**을 사용자 입력 범위로 지원한다.

주요 예측 태스크는 다음과 같다.

- 발생형태 분류
- 재해정도 분류
- 질병종류 분류
- 세부 질병종류 분류
- 질병 기반 재해정도 분류

무작위 데이터 분할 대신 **2023년 이하 데이터를 학습에 사용하고 2024년 이후 데이터를 테스트에 사용하는 시간 분할 방식**을 적용하여 실제 미래 데이터에 대한 일반화 성능을 확인했다.

또한,

- Optuna TPE 기반 50회 하이퍼파라미터 탐색
- 클래스 불균형 보정
- Early Stopping
- SHAP 기반 설명 가능성 제공

을 적용했다.

SHAP Explainer는 서버 기동 시 미리 생성해 캐싱하도록 개선했다.
기존에는 요청마다 Explainer를 생성해 예측 응답이 수 초 이상 지연되는 병목이 있었으나
캐싱 적용 후 반복 요청에서는 해당 초기화 비용이 제거되어 응답 지연을 크게 줄였다.

다만 현재 ML 모델의 macro F1 성능은 충분히 높지 않기 때문에, **ML 출력만으로 안전 여부나 법적 판단을 결정하지 않는다.**

SafeWork AI에서 ML은 **위험 가능성과 점검 우선순위를 제공하는 보조 신호**로 사용하고, 체크리스트와 통계 기반 위험도 및 실제 법령 근거를 함께 사용한다.

### 법령 RAG

법령 상담은 다음 두 검색 방식을 결합한다.

**Keyword Search**

- PostgreSQL `pg_trgm`
- 정확한 법률용어 및 부분일치 검색

**Semantic Search**

- `jhgan/ko-sroberta-multitask`
- Sentence Transformers
- FAISS
- 코사인 유사도 검색

두 검색 결과를 조문 단위로 통합하고 중복 결과를 제거한다.

사용자 질문에서 핵심 키워드를 추출·확장하고 중요도에 따라 정렬하여 긴 질문에서도 중요한 검색어가 제외되는 문제를 줄였다.

생성형 AI가 자유롭게 법률 내용을 만들어내지 않도록,

**사용자 질문 → 관련 조문 검색 → 검색 결과 확정 → 검색된 조문 기반 답변 생성**

순서로 처리한다.

생성형 AI 호출에 실패한 경우에는 `RETRIEVAL_ONLY` 상태로 전환하여 검색된 법령 조문만 제공한다.

| 법령 답변 | 생성 모델 지식에 의존 가능 | 검색된 실제 조문을 근거로 답변 |
| 근거 확인 | 확인하기 어려움 | 법령명·조문 번호 제공 |
| 재해 데이터 | 제한적 | 실제 산업재해 약 64만 건 활용 |
| 예방 점검 | 일반적인 체크리스트 | 작업 범주별 25~35개 맞춤 문항 |
| 사고 이후 | 검색을 다시 수행해야 함 | 즉시조치→법적의무→행정처리 연결 |
| AI 장애 | 기능 전체 실패 가능 | 검색·DB 기반 결과로 Graceful Degradation |
| 위험도 | 단일 AI 결과 중심 | 통계·체크리스트·ML 신호 결합 |
| 설명 가능성 | 결과만 제공 | SHAP 및 법적 근거 제공 |

SafeWork AI의 가장 큰 차별점은 **“AI가 답을 생성한다”는 사실 자체가 아니라, 답을 검증할 수 있는 근거가 함께 제공된다는 것**이다.

또한 예방 기능만 제공하거나 법령 검색만 제공하는 단일 목적 서비스와 달리 **사고 전과 사고 후를 하나의 흐름으로 연결했다.**


## 1.5. 사회적가치 도입 계획

SafeWork AI가 해결하고자 하는 핵심 문제는 **사업장 규모에 따른 안전 정보와 전문성의 격차**이다.

대규모 사업장은 안전관리 조직과 전문 인력을 확보할 수 있지만, 소규모 사업장은 동일한 수준의 정보 탐색과 대응 체계를 갖추기 어렵다.

SafeWork AI는 공개된 산업재해·법령·행정·정책 데이터를 비전문가도 이해할 수 있는 형태로 제공함으로써 다음과 같은 사회적 가치를 목표로 한다.

### 안전 정보 접근성 향상

사업주가 여러 법령과 정부 사이트를 직접 검색하는 대신 사업장 상황과 관련된 핵심 정보와 근거를 한 화면에서 확인할 수 있도록 한다.

### 예방 중심의 안전관리 지원

사고 발생 이후의 책임 확인에 그치지 않고 실제 재해사례에서 도출한 체크리스트와 예방가이드를 통해 사고 발생 전에 위험요인을 확인하도록 지원한다.

### 중소 사업장의 안전관리 격차 완화

전문 안전인력을 확보하기 어려운 소규모 사업장이 최소한의 안전 점검과 법령 정보에 쉽게 접근할 수 있도록 한다.

### 공공데이터 활용 가치 확대

산업재해 통계, 법령, 판례, 행정규칙, 정부 지원사업 등 개별적으로 공개된 데이터를 하나의 서비스 흐름으로 연결하여 공공데이터의 실질적인 활용성을 높인다.

### 향후 확장 계획

현재 지원 범위인 제조업·건설업·운수창고통신업·전기가스 관련 업종을 기반으로 데이터가 확보되는 대로 서비스업 등 추가 업종으로 확장할 계획이다.

장기적으로는 현장 데이터와 사용자 피드백을 축적하여 체크리스트 분류 정확도와 위험도 모델을 개선하고, 정부 안전지원 사업과의 연계 기능도 강화할 수 있다.

##### 입력

사용자는 사업장의 기본정보와 실제 현장에서 수행하는 작업·위험 범주를 선택한다.

- 업종
- 지역
- 사업장 규모
- 현장 작업·위험 범주

작업·위험 범주는 복수로 선택할 수 있다.

##### 처리

서비스는 사용자가 선택한 정보를 기반으로 서비스용 SIF 98개 가운데 해당 사업장에서 우선적으로 확인해야 할 점검 문항을 선별한다.

문항은 다음 우선순위에 따라 구성한다.

1. 공통 중대 SIF
2. 사용자가 선택한 작업·위험 범주의 SIF
3. 해당 업종의 고위험 SIF

이후 위험가중치를 반영하여 최종 **25~35개의 맞춤 점검 문항**을 제공한다.

##### 결과

전체 문항을 모두 확인하는 대신, 사용자는 자신의 현장과 관련성이 높은 핵심 문항을 중심으로 점검을 진행할 수 있다.


#### STEP 2 - 맞춤 체크리스트 및 위험도 진단
<img width="842" height="943" alt="image" src="https://github.com/user-attachments/assets/67027761-322c-4805-80db-7b96159903e4" />

STEP 1에서 선별된 SIF 문항을 이용해 사업장의 실제 안전 상태를 점검한다.

##### 맞춤 SIF 체크리스트

각 체크리스트 항목은 다음 정보로 구성된다.

```text
재해유형
SIF 식별번호
위험가중치
점검 질문
관련 작업
관련 재해사례 보기
```

사용자는 각 문항에 대해 다음 세 가지 중 하나를 선택한다.

- **예**
- **아니오**
- **해당 없음**

`해당 없음`으로 응답한 항목은 위험도 계산에서 제외된다.

또한 진행률을 통해 전체 문항 가운데 몇 개를 응답했는지 실시간으로 확인할 수 있다.

##### 위험도 진단
<img width="1668" height="1029" alt="image" src="https://github.com/user-attachments/assets/07919b0e-5c5b-462b-8d96-f0c7e77c0e30" />

체크리스트 제출과 동시에 서버에서 최종 위험도 진단을 수행한다.

진단 결과에서는 다음 정보를 제공한다.

**최종 위험도**

- 위험등급
- 위험점수

**위험 구성**

- 동종 사업장 기본 위험
- 우리 사업장의 체크리스트 미비 위험

**주요 위험정보**

- 최우선 재해유형
- 진단 방식
- 통계 매칭 수준

**종합 위험유형 비중**

각 재해유형이 현재 사업장의 진단 결과에서 차지하는 비중을 제공한다.

예:

```text
떨어짐      24.9%
끼임        17.8%
업무상질병  17.4%
```

체크리스트에서 직접 확인된 미비 항목과 동종 사업장의 위험 특성이 함께 반영된다.

**예상 피해 심각도**

예:

```text
6개월 이상   34.8%
91~180일     31.4%
29~90일      25.8%
```

ML 모델의 결과는 안전 여부를 단독으로 판정하기 위한 값으로 사용하지 않는다.

통계 기반 기본 위험과 실제 체크리스트 미비 항목을 중심으로 진단하며, ML 예측은 **주요 위험유형과 예상 피해 심각도를 파악하기 위한 보조 신호**로 활용한다.


#### STEP 3 - 맞춤 유사 재해사례
<img width="1462" height="912" alt="image" src="https://github.com/user-attachments/assets/a11fbdb3-2318-423d-bce9-bd53c931d21e" />

위험도 진단이 완료되면 현재 사업장과 관련성이 높은 실제 재해사례를 제공한다.

추천에는 다음 정보가 반영된다.

- 사업장 세부정보
- 체크리스트 미비 항목
- 주요 위험 재해유형
- 현장 작업 특성

각 사례에서는 다음 정보를 확인할 수 있다.

- 사례 번호
- 유사도
- 실제 사고 발생 과정
- 관련 설비 및 작업
- 재발 방지 대책

예를 들어 지게차, 적재, 고소작업과 관련된 위험이 확인된 사업장에는 실제 지게차·추락·끼임 사고사례와 해당 사고의 재발 방지 대책을 함께 제공한다.

이를 통해 사용자는 단순히 위험점수를 확인하는 데 그치지 않고,

> **“우리 현장과 비슷한 상황에서 실제로 어떤 사고가 발생했는가”**

를 확인할 수 있다.


#### STEP 4 - 맞춤 예방가이드 및 PDF 리포트
<img width="866" height="787" alt="image" src="https://github.com/user-attachments/assets/436ea3a1-2b5a-49bf-90b9-ae40d7479589" />

##### 맞춤 예방가이드

체크리스트에서 확인된 미비 항목을 재해유형별로 집계하고 위험도가 높은 순서대로 개선 우선순위를 제공한다.

예:

```text
1순위 - 떨어짐
2순위 - 넘어짐
3순위 - 무너짐
```

각 우선순위에서는 다음 정보를 제공한다.

- 재해유형
- 미비 항목 개수
- 전체 미비 위험 중 해당 유형의 비중
- 세부 점검 문항
- 위험가중치
- 관련 법령 및 조문

이 단계의 목적은 단순히

> “위험도가 높습니다.”

라고 알려주는 것이 아니라,

> **“어떤 항목이 부족하며, 무엇부터 개선해야 하고, 그 개선의 법적 근거가 무엇인지”**

를 제공하는 것이다.

### 별도 핵심 기능

안전진단 4단계와 별도로 SafeWork AI는 **법령 상담**과 **사고 대처** 기능을 제공한다.


#### 법령 상담
<img width="707" height="698" alt="image" src="https://github.com/user-attachments/assets/4578de85-c699-4b56-b9c8-b0ff74f84d8e" />

사용자는 산업안전과 관련된 질문을 자연어로 입력할 수 있다.

예:

> “사다리에서 작업할 때 어떤 안전조치를 해야 하나요?”

서비스는 사용자의 질문에 대해 키워드 검색과 의미 기반 검색을 함께 수행한다.

##### 처리

1. 사용자 질문의 핵심어 추출 및 확장
2. PostgreSQL `pg_trgm` 기반 키워드 검색
3. Sentence Transformers + FAISS 기반 의미 검색
4. 관련 법령 조문 통합 및 중복 제거
5. 검색된 조문을 근거로 생성형 AI가 답변 작성

##### 결과

사용자는 다음 정보를 확인할 수 있다.

- 질문에 대한 자연어 설명
- 관련 법령명
- 조문 번호
- 관련 조문 내용

생성형 AI가 임의로 법적 근거를 선택하지 않고, 검색 시스템이 먼저 실제 법령 조문을 확정한 뒤 해당 범위 안에서만 답변을 생성한다.

또한 생성형 AI 호출이 실패한 경우에도 `RETRIEVAL_ONLY` 방식으로 검색된 법령 조문은 계속 제공한다.

  <sub>사고 상황을 입력하면 관련 법령을 기반으로 법적 의무·행정 절차·위험 정보를 안내합니다.</sub>

사고가 발생한 직후 사업주가 확인해야 할 정보를 행동 순서에 따라 제공한다.

사고 상황과 피해 정보를 입력하면 관련 법령과 행정절차를 조회하여 다음 세 영역으로 안내한다.

##### 즉시 조치

- 현장에서 우선 수행해야 할 안전조치
- 추가 피해 방지를 위한 조치

##### 법적 의무

- 사고와 관련된 법령
- 관련 조문
- 사업주가 확인해야 할 법적 의무

##### 행정 처리

- 신고·보고 대상
- 담당 기관
- 처리 기한
- 관련 법적 근거
- 필요한 행정 절차

사고 직후 여러 기관과 법령을 직접 검색해야 하는 부담을 줄이고,

> **“무엇을 먼저 해야 하는지, 누구에게 언제까지 알려야 하는지”**

를 한 화면에서 확인할 수 있도록 구성했다.


### SafeWork AI 핵심 서비스 흐름

#### 안전 진단

> **현장을 선택한다 → 실제 위험을 점검한다 → 위험도를 확인한다 → 비슷한 실제 사고를 확인한다 → 무엇을 고칠지 법령 근거와 함께 확인한다 → 결과를 PDF로 남긴다.**

#### 사고 전·후 통합 지원

> **사고 전에는 위험을 점검하고 개선하며, 사고가 발생한 이후에는 필요한 법령과 대응 절차를 확인한다.**

SafeWork AI는 단순한 사고확률 예측 서비스가 아니라 **사고 전 예방부터 사고 후 대응까지 하나의 흐름으로 연결하는 산업안전 관리 지원 서비스**를 목표로 한다.

## 3.5. AI 도구 활용

### ① 산업재해 예측 모델 구축

산업재해 데이터를 기반으로 LightGBM 모델을 학습하여 사업장 특성에 따른 주요 재해 유형과 심각도 관련 위험 신호를 제공한다.

모델 학습 시 Optuna를 이용한 하이퍼파라미터 탐색과 클래스 불균형 처리를 적용했으며, SHAP 값을 통해 어떤 입력 특성이 예측에 영향을 주었는지 확인할 수 있도록 했다.

### ② AI 기반 법령 검색

사용자의 질문과 법령 문장 사이의 의미적 유사도를 계산하기 위해 `jhgan/ko-sroberta-multitask`를 사용했다.

FAISS 인덱스를 구축하여 3,608개 법령 조문을 빠르게 검색하며, PostgreSQL `pg_trgm` 키워드 검색과 결합해 정확한 법률용어와 자연어 표현을 함께 처리한다.

### ③ 생성형 AI 기반 법령 설명

Gemini는 법령 자체를 선택하는 역할이 아니라 **검색 시스템이 선택한 법령을 사용자가 이해하기 쉽게 설명하는 역할**을 수행한다.

이를 통해 생성형 AI가 존재하지 않는 법령이나 조문을 자유롭게 만들어낼 가능성을 구조적으로 줄였다.

생성 API가 실패하면 검색된 조문만 제공하도록 하여 생성형 AI가 서비스의 단일 장애점이 되지 않도록 설계했다.

### ④ 체크리스트-법령 연결

835개 안전점검 문항에 어떤 법령이 관련되는지를 연결하기 위해 임베딩 코사인 유사도로 후보 조문을 찾고 LLM을 이용해 관련성을 추가 검토했다.

이를 통해 안전점검 결과에서 단순히 “미흡”이라고 표시하는 대신 **왜 개선해야 하는지에 대한 법적 근거**를 함께 제공할 수 있도록 했다.

### ⑤ AI 코딩 도구 활용

**주요 개발 AI 도구:** Claude Code, OpenAI Codex, ChatGPT, Figma Make, Prism

AI 코딩 도구는 다음과 같은 개발 보조 과정에서 활용하였다.

- 반복적인 코드 초안 작성
- API DTO 및 테스트 케이스 검토
- SQL 및 예외처리 로직 검토
- 코드 리팩터링 아이디어 도출
- 기술 문서 및 API 명세 정리

AI가 생성한 코드는 그대로 사용하는 것이 아니라 직접 코드 리뷰하고 실제 실행·통합 테스트를 통해 검증하는 방식으로 활용했다.

AI 활용 및 생성 코드 검증에 대한 상세 내용은
[docs/ai-usage.md](./docs/ai-usage.md)에서 확인할 수 있습니다.

## 3.6. 테스트 및 검증

### Backend

- 총 **79건의 테스트 통과**
- Testcontainers를 통해 실제 PostgreSQL 환경에서 통합 테스트
- 저장소의 실제 스키마를 테스트 환경에 적재
- PostgreSQL 함수 및 전용 타입까지 검증

인메모리 DB로 대체하지 않은 이유는 서비스의 핵심 로직이 PostgreSQL 함수, enum, 배열 및 전용 기능에 의존하기 때문이다.

### 오류 처리

PostgreSQL의 SQLSTATE를 분석하여 사용자가 수정할 수 있는 입력 오류와 서버 내부 오류를 구분했다.

예를 들어,

- Foreign Key 위반 → 잘못된 선택값 → `400`
- Unique 위반 → 중복 입력 → `400`
- Check Constraint 위반 → 허용 범위 오류 → `400`
- 예상하지 못한 NOT NULL 위반 → 서버 구현 오류 가능성 → `500`

으로 처리한다.

사용자가 해결할 수 없는 서버 오류를 단순히 `400`으로 감추지 않고 서버 로그에 스택 트레이스를 남길 수 있도록 설계했다.


## 3.7. 현재 범위와 한계

SafeWork AI는 해커톤 기간 내 실제 동작하는 End-to-End 서비스를 만드는 것을 우선 목표로 했다. 따라서 다음 한계가 존재한다.

### ML 예측 성능

일부 다중분류 태스크의 macro F1 성능이 충분히 높지 않다.

예를 들어 제조업 발생형태 23개 클래스 예측은 정확도와 별개로 macro F1이 낮아 소수 클래스 분류 성능에 한계가 있다.

따라서 SafeWork AI는 ML 예측 확률을 **사고 발생을 단정하는 값**으로 사용하지 않고 **점검 우선순위를 결정하기 위한 보조 신호**로 제한한다.

### 체크리스트 범주 선별

현재 체크리스트 선별에는 키워드 기반 규칙이 일부 사용된다.

데모 범위에서는 정상적으로 동작하지만 실서비스에서는 각 점검 문항에 정규화된 작업 범주 메타데이터를 추가하여 문구 변경에 영향을 받지 않는 구조로 개선할 필요가 있다.

### 지원 업종

ML 모델은 6개 업종군을 기준으로 학습했지만 현재 웹 서비스의 사용자 입력 및 진단 흐름은 다음 4개 업종을 지원한다.

- 제조업
- 건설업
- 운수·창고·통신 관련 업종
- 전기·가스 관련 업종

서비스업 등은 현재 지원 범위 밖이다.

### Frontend Test

백엔드는 79건의 테스트를 구축했지만 프론트엔드 자동화 테스트는 아직 구축하지 못했다.

향후 React Testing Library 및 E2E 테스트를 통해 주요 사용자 흐름을 검증할 계획이다.

### 배포 환경

현재 해커톤 시연 환경은 로컬 서버와 터널링을 기반으로 구성되어 있다.

실서비스에서는 서버 이중화, 모니터링, 로그 관리, HTTPS, Secret 관리, 자동 배포 등의 인프라 보강이 필요하다.

### 법률적 한계

SafeWork AI가 제공하는 법령 및 행정절차 정보는 사용자의 판단을 돕기 위한 참고자료이다.

특히 다음 두 기준은 구분해야 한다.

- **산업안전보건법상 ‘중대재해’**
- **중대재해처벌법상 ‘중대산업재해’**

두 법률은 부상기간과 직업성 질병자 수 등 판정 기준이 서로 다르므로 서비스 화면과 데이터베이스에서도 적용 법률을 명확히 표시해야 한다.

## 4.1. 사전 요구사항

다음 소프트웨어가 필요하다.

- Git
- Docker / Docker Compose
- Java 17
- Python 3.x
- Node.js / npm

전체 산업재해 원본 데이터 덤프는 용량 문제로 Git 저장소에 포함시키지 못하였다.

필요한 경우 별도로 제공되는 데이터 덤프를 `database/dump/` 경로에 배치하거나 저장소의 데이터 수집·적재 스크립트를 이용한다.


## 4.2. Repository Clone

```bash
git clone https://github.com/PNU-2026-AI-Hackathon/pnuai-a-07-ai.git
cd pnuai-a-07-ai
```


## 4.3. PostgreSQL + Backend 실행

루트 디렉토리에서 다음 명령을 실행한다.

```bash
docker compose up -d
```

현재 Docker Compose 구성은 다음 서비스를 실행한다.

- PostgreSQL : `5432`
- Spring Boot Backend : `8080`

서비스 상태 확인:

```bash
docker compose ps
```

로그 확인:

```bash
docker compose logs -f
```

DB를 완전히 초기화하여 다시 적재해야 하는 경우:

```bash
docker compose down -v
docker compose up -d
```


## 4.4. ML / RAG 서버 실행

```bash
cd mlserver

python -m venv .venv
```

Windows:

```bash
.venv\Scripts\activate
```

macOS / Linux:

```bash
source .venv/bin/activate
```

의존성 설치:

```bash
pip install -r requirements.txt
```

서버 실행:

```bash
uvicorn app.main:app --reload --port 8000
```

실행 후 FastAPI Swagger 문서를 통해 ML/RAG API를 확인할 수 있다.

```
http://localhost:8000/docs
```

FAISS 인덱스가 없는 경우 첫 실행 시 구축되며, 필요한 경우 사전에 인덱스 생성 스크립트를 실행할 수 있다.


## 4.5. Frontend 실행

새 터미널에서 다음을 실행한다.

```bash
cd frontend

npm install
npm run dev
```

Vite 개발 서버가 실행된 뒤 출력되는 로컬 주소로 접속한다.


## 4.6. Backend Test

Backend 통합 테스트는 Docker가 실행 중인 환경에서 수행한다.

macOS / Linux:

```bash
cd backend
./gradlew test
```

Windows:

```bash
cd backend
gradlew.bat test
```

Testcontainers가 실제 PostgreSQL 컨테이너를 생성하여 테스트한다.

현재 기준 커밋에서 **79건의 백엔드 테스트가 통과**한다.

# 7. 해커톤 참여 후기

### 구현서 - 팀장 / Backend

이번 해커톤에서는 팀장과 백엔드 개발을 맡아 DB, ML, 프론트엔드에서 각각 구현한 기능을 하나의 서비스 흐름으로 연결하는 역할을 수행했습니다. 단순히 각 기능이 동작하는 데서 끝나는 것이 아니라 사용자가 사업장 정보를 입력하고 체크리스트를 수행한 뒤 위험도 진단, 유사 재해사례, 예방가이드, 법령 상담과 사고 대처까지 자연스럽게 이어지도록 전체 구조를 설계하는 과정에서 많은 것을 배울 수 있었습니다.

특히 산업안전과 같이 잘못된 정보가 실제 판단에 영향을 줄 수 있는 분야에서는 AI의 성능만큼이나 결과의 근거와 안정성이 중요하다는 점을 느꼈습니다. 그래서 생성형 AI가 모든 판단을 내리도록 하기보다 실제 법령과 공공데이터를 먼저 검색하고 AI는 이를 설명하는 역할로 제한했습니다. 또한 ML이나 생성형 AI가 정상적으로 동작하지 않는 상황에서도 가능한 범위의 결과를 제공하도록 대체 흐름을 구성하면서 실제 서비스에서의 장애 대응과 신뢰성에 대해서도 고민할 수 있었습니다.

짧은 기간 동안 서로 다른 분야를 담당한 팀원들과 API와 데이터 구조를 조율하고 기능을 통합하는 과정이 쉽지만은 않았지만 각자의 결과물이 하나의 완성된 서비스로 연결되는 경험이 특히 의미 있었습니다. 이번 해커톤을 통해 좋은 서비스를 만들기 위해서는 새로운 기술을 많이 사용하는 것보다 사용자가 실제로 필요로 하는 문제를 정의하고 기술의 한계를 인정하면서도 신뢰할 수 있는 방식으로 해결하는 것이 더 중요하다는 것을 배웠습니다.

### 강주호 - Database / Data

이번 프로젝트를 진행하면서 데이터베이스가 단순히 데이터를 저장하는 공간이 아니라 서비스의 예측·진단·예방·대응 로직을 실제로 작동하게 하는 핵심이라는 점을 체감했습니다. 처음에는 여러 출처의 데이터를 하나의 구조로 정리하고 백엔드와 ML이 바로 사용할 수 있는 형태로 함수를 설계하는 과정이 생각보다 어렵게 느껴졌습니다.

AI 도구를 적극적으로 활용하면서 설계와 구현 속도를 높일 수 있었지만 생성된 코드가 항상 요구사항에 정확히 맞는 것은 아니었습니다. 실제로 실행해 보면 테이블 간 어휘가 달라 결과가 비거나 백엔드가 기대하는 반환 형식과 함수의 출력이 맞지 않는 경우도 있었습니다. 이러한 문제를 하나씩 확인하고 수정하면서 AI가 코드를 대신 완성해 주는 도구라기보다 제가 데이터 구조와 요구사항을 명확히 전달하고 결과를 직접 판단해야 하는 보조 도구라는 점을 배웠습니다. 또한 결과가 그럴듯하게 나오는 것에서 끝나지 않고 실제 데이터로 근거를 확인하는 과정이 중요하다는 것도 알게 되었습니다.

이번 프로젝트를 통해 부족한 부분도 많이 확인했지만 흩어져 있던 데이터를 하나의 구조로 정리하고 팀원들의 백엔드·ML·프론트엔드 기능과 연결해 실데이터 기반의 서비스 흐름을 완성했다는 점에서 의미가 있었습니다. 앞으로는 AI가 생성한 코드를 더 정확하게 이해하고 검증할 수 있도록, 테스트 작성과 데이터베이스 설계에 대한 공부를 계속해 나가겠습니다.

### 이승원 - ML / RAG

AI 도구를 활용하면서 코드 작성과 원인 분석 속도는 크게 빨라졌지만 그 결과를 그대로 믿기보다 근거로 재검증하는 절차가 훨씬 더 중요하다는 것을 체감했습니다. AI가 "이게 원인입니다", "이만큼 개선됐습니다"라고 말하는 것과, git 이력이나 실제 실행 결과로 확인된 것은 다른 문제였습니다. 특히 여러 팀원이 함께 만든 코드베이스에서는 AI가 전체 코드를 훑어 답을 주기 때문에 오히려 "내가 실제로 한 일"의 경계가 흐려지기 쉽다는 점도 알게 되었습니다. 그래서 성과를 정리할 때마다 git 커밋 이력을 기준으로 본인의 기여 범위를 다시 확인하는 습관을 갖게 되었습니다.

이 과정에서 AI는 코드를 대신 완성해 주는 도구라기보다 원인을 빠르게 좁혀주고 근거를 정리해 주는 보조 도구이며 그 결과를 검증하고 최종적으로 책임지는 것은 결국 본인의 몫이라는 점을 배웠습니다. 앞으로도 AI 도구를 적극적으로 활용하되, 주장은 반드시 로그·커밋 이력·실측 데이터 같은 근거로 재확인하는 방식을 유지하려 합니다.

### 신찬우 - ML / Modeling

정보컴퓨터학과 학생들과의 융합 협업을 통해 평소 데이터 분석 과정에서는 경험하기 어려웠던 실제 서비스 구현 전반을 함께 경험할 수 있었습니다. ML 예측 모델과 데이터 파이프라인이 백엔드 API, 데이터베이스 스키마, 프론트엔드와 어떻게 연결되는지 직접 확인하면서 데이터 분석 역량이 실제 서비스에서 어떤 방식으로 활용되고 어떤 제약을 받는지 구체적으로 이해할 수 있었습니다. 특히 ML 모델의 입력 피처 설계가 DB 스키마 및 사용자 입력 흐름과 긴밀하게 연결되어 있음을 협업 과정에서 체감하였으며 이를 통해 데이터 분석가로서 서비스 전체 구조를 고려한 설계의 중요성을 배울 수 있었던 뜻깊은 경험이었습니다.

### 곽동헌 - Frontend

이번 프로젝트를 진행하면서 처음에는 제가 생각한 화면과 기능을 실제 코드로 구현하는 과정이 생각보다 어렵게 느껴졌습니다. 특히 프론트엔드만 만드는 것이 아니라 백엔드와 ML 결과가 어떤 형태로 전달되는지 이해하고 이를 사용자가 자연스럽게 이용할 수 있는 화면 흐름으로 연결하는 과정이 가장 어려웠습니다.

AI 도구를 적극적으로 활용하면서 개발 속도를 높일 수 있었지만 생성된 코드가 항상 프로젝트의 요구사항에 정확히 맞는 것은 아니었습니다. 실제로 실행해 보면 화면 이동이 자연스럽지 않거나 프론트엔드와 백엔드의 데이터 형식이 맞지 않는 경우도 있었습니다. 이러한 문제를 하나씩 확인하고 수정하면서 AI가 코드를 대신 완성해 주는 도구라기보다 제가 요구사항을 명확하게 전달하고 결과를 직접 판단해야 하는 보조 도구라는 점을 배웠습니다.

처음에는 생성된 코드를 이해하는 데 시간이 필요했지만 프로젝트를 진행하면서 라우팅, Context API, API 요청과 응답, 컴포넌트 간 데이터 전달 구조를 조금씩 이해할 수 있게 되었습니다. 또한 단순히 화면이 보이는 것에서 끝나는 것이 아니라 실제 사용자 흐름과 오류 상황까지 확인하는 과정이 중요하다는 것도 알게 되었습니다.

이번 프로젝트를 통해 부족한 부분도 많이 확인했지만 직접 문제를 찾아 수정하고 팀원들의 백엔드 및 ML 기능과 프론트엔드를 연결해 하나의 서비스 흐름을 완성했다는 점에서 의미가 있었습니다. 앞으로는 AI가 생성한 코드를 더 정확하게 이해하고 검증할 수 있도록 테스트 작성과 코드 구조에 대한 공부를 계속해 나가겠습니다.

# 프로젝트가 지향하는 것

SafeWork AI의 목표는 AI가 안전관리자의 판단을 대신하는 것이 아니다.

**흩어져 있는 산업재해 데이터와 법령을 연결하고 사용자가 판단에 필요한 근거를 빠르게 찾을 수 있도록 만드는 것**이다.

모델이 확신하지 못하는 영역에서는 확률을 과장하지 않고, 생성형 AI가 실패하면 실제 법령을 그대로 제공하며, 위험 여부가 불명확하면 필요한 안전정보를 유지한다.

> **SafeWork AI - 사고가 나기 전에 무엇을 점검해야 하는지, 사고가 난 뒤 무엇을 해야 하는지 근거와 함께 알려주는 AI 안전관리 조력자.**
>
